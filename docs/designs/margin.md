## Problem Statement

Ella builds mostly with AI (Claude Code wrote much of Atlas and learningtool). When she opens code she didn't write, the first thing she can't figure out is **what this part does**. Then comes why it's built this way, then which design decisions shaped it. Today that understanding lives in chat transcripts that disappear. She rebuilt the decisions behind learningtool by hand, as a 27-decision design doc.

Her original pitch: "somewhere you can work alongside your code, making note of why this is happening, why you made these decisions, and then keep track of important design decisions." She sharpened it during the session. It should live inside VS Code, and "i dont want this to be static, i want it to adapt and learn constantly as I write my code." She also added a front door: "visualizing at a high level what my code is doing... where I can click on a part and it points me to that part of the code."

## What Makes This Cool

- **Map → Part → Line.** You open a repo and see a map of 8 or fewer boxes, built from the real code structure. Click a box and you're in that code. Select a block, guess what it does, and see the explanation next to your guess. What survives becomes a note pinned to those lines.
- **Predict, then reveal.** The line where your guess and the code disagree ("You missed: removed claims are named, not dropped") is the learning moment. learningtool uses the same move.
- **It stays honest as code changes.** Edit a function and its note turns amber in the gutter. Its box on the map turns amber too. Notes are labeled `drafted` or `checked by you`, never `verified`.
- **Recruiter line:** "Copilot explains your code and forgets. Note extensions remember but can't explain. This turns explanations into notes that stay true as the code changes."

## Constraints

- Solo builder working with Claude Code. No hackathon date yet, so build for her own daily use first and cut the demo later.
- Audience: recruiters and engineering teams (health-AI, frontier labs, medtech). The 60-second GIF is the artifact they'll see.
- VS Code extension (TypeScript). Python repos first.
- Code goes to an LLM API only in a workspace where AI is explicitly enabled; exactly what each command sends is listed under Privacy and trust. The demo runs on **learningtool**, which is public. Atlas holds candid notes on real people, so AI is never enabled there.
- The API key is stored in VS Code SecretStorage or an env var, never in settings files, notes, or chat.

## Premises (agreed)

1. The job is understanding code you didn't write, in this order: what it does, then why, then design decisions. Notes are where understanding accumulates; they aren't the product.
2. **(Revised after second opinion)** Predict, then reveal. The user types an optional one-line guess, then the drafted explanation appears beside it, citing exact line ranges. "Just show me" skips the guess, and the note stays `drafted`. Only a note you predicted (a guess of 5+ words) or edited earns `checked by you`; the full state machine is under Mechanisms. Nothing is ever `verified`.
3. It's a VS Code extension: Comments API threads in the gutter, hover, CodeLens, and a sidebar webview. Notes are plain files in the repo (`.why/`). The files are the truth, as in Atlas.
4. In v1, "adapts as I write" means three things. Notes move with edits. Notes turn amber when the code under them changes. New uncovered code gets a margin question. No model training.
5. Distribution: a public GitHub repo, a `.vsix` on GitHub Releases, then VS Code Marketplace and Open VSX, plus a 60-second GIF on learningtool.
6. **(Added by Ella)** A high-level, clickable map of what the code does is the front door. The extension pulls the real structure from the language server (document symbols plus call hierarchy). The LLM groups that structure into 8 or fewer named boxes, and each box cites its files. Clicking a box reveals its code. Note counts and staleness show on the boxes.

## Mechanisms (v1)

### Explain and compare
- **Draft call** (it never sees the guess). The prompt carries the selection with **absolute file line numbers**, the file path, and the name of the enclosing symbol. Nothing else from the repo is sent. It returns `claims: [{text, startLine, endLine}]` in absolute lines.
- **Range validation.** A claim that partly overlaps the selection is clipped to the selection. A claim with no overlap, or with `startLine > endLine`, is dropped. If zero claims survive, the extension retries once automatically. If there are still none, the thread says "Couldn't produce a cited explanation for this selection" with a Retry button, and nothing is saved.
- **Compare call** (runs only when a guess was typed). Input: the guess plus the validated claims. Output: `{verdict: match | partial | miss, missed: [{text, claimIndex}]}`. Every missed item must point at a validated claim, so it inherits that claim's line citation; items that don't are dropped. The "You missed" line renders these items. With no guess there is no compare call and no "You missed" line.
- For the self-check log, "guess differed" means a verdict of `partial` or `miss`.

### Note status (state machine)
- **Save with no guess, or with a guess under 5 words:** `drafted`.
- **Save with a guess of 5+ words, or after editing the draft text:** `checked by you`.
- **Code under the anchor changes** (hash mismatch): a persisted `stale` flag is set. The label becomes "checked, then code changed" or "drafted, then code changed". A stale note is never shown as plainly checked. CodeLens wording follows the same rule.
- **Resolving stale** (actions on the thread and the CodeLens):
  - **Re-check** re-runs predict-then-reveal on the current code. It replaces the draft, sets status by the rules above, updates the hash, and clears the flag.
  - **Still true** updates the hash and clears the flag, but drops the status to `drafted`, because nothing was re-checked.
  - **Discard** deletes the note.
- **Orphaned** (anchor can't be found safely; see below): shown in the Notes tab with Re-link and Discard. Never silently dropped.
- A map box is amber while any note assigned to it is stale.

### Note storage and anchor persistence
- **One file per note:** `.why/notes/<id>.md`, where `id` is a short random ID. Frontmatter holds `id`, `file` (repo-relative), `anchor {startLine, endLine, hash, headSnippet, tailSnippet}`, `status`, `stale`, `guess`, `created`, and `updated`. `hash` is the sha256 of the anchored text with whitespace normalized; the snippets are its first and last 3 lines. The body is the note text with its line citations.
- **Live edits:** incremental edits you type in the editor shift anchors in memory. *Those shifts* are written to disk only on `onDidSaveTextDocument`, and only the changed fields. On close-without-save or revert, in-memory shifts are discarded and the on-disk state is reloaded.
- **Notes always describe saved file content (the one rule for dirty buffers).** While a source document is dirty, every anchor-changing action on it is queued in memory and applied when the file is saved. That covers saving a new note, Re-check, Still true, Re-link, and any re-anchor. On revert or close-without-save, the queue is discarded along with the in-memory shifts. So a note file never holds a hash or range for text that was never saved.
- **File hashes live in an index, not in notes.** Per-file content hashes go in a single uncommitted index in `workspaceState` (`file → fileHash`), not in note frontmatter, so `fileHash` is dropped from the note format. The index is refreshed on every save and after every re-anchor. A note file only changes when its own anchor, status, or text changes, which keeps `.why/` diffs small. An undo back to the saved state matches the index, so it isn't misread as a reload.
- **Outside edits to a dirty file** (Claude Code or `git pull` touching a file you have unsaved edits in): VS Code doesn't reload it, and the watcher event only marks the file "disk changed" without re-anchoring. VS Code's own save-conflict dialog decides between overwrite and take-disk. After either outcome (your save wins, or the buffer reloads from disk), the normal path runs once: compare the content to the index, then re-anchor if they differ.
- **Everything else is written immediately**, changed fields only, for files that are not dirty: re-anchor results, stale and orphan transitions, rename updates to `file`, and the Re-check, Still true, Re-link, and Discard actions. None of these wait for a document save.
- **Citations move with the anchor.** Claim citations are stored in frontmatter as `citations: [{claimIndex, startOffset, endOffset}]`, line offsets relative to `anchor.startLine`. Absolute line numbers are computed from the current anchor at display time, so a note shifted 40 lines down shows correct chips. For a stale note, the chips render greyed with "lines may have changed". An orphaned note shows its citations as text only, with no jump.
- **Renames:** a rename inside VS Code (`workspace.onDidRenameFiles`) updates `file`. A rename outside VS Code (for example `git mv` arriving through a pull): when a note's file is missing, newly created files are searched for an **exact** hash match. If none is found, the note becomes orphaned with a Re-link action.

### Outside edits, re-anchoring, staleness
- **Detecting outside edits:**
  1. On activation and on document open, compare the indexed `fileHash` to the current file.
  2. A `FileSystemWatcher` covers files that have notes.
  3. **Reload detection.** VS Code reloads an open, clean document after a `git pull`, branch switch, or Claude Code edit by applying a computed minimal edit, not a whole-document replacement. So the extension doesn't look at the shape of the change. Any change event after which `document.isDirty` is `false` (the text now matches disk) and the indexed `fileHash` differs from the new content counts as a reload.
  Outside edits route to re-anchoring, never to incremental shifting. On a reload, in-memory shifts are buffered per event, and if the event turns out to be a reload, the buffered shift is thrown away and re-anchoring runs against the stored on-disk anchors. When the watcher (rule 2) and the reload event both fire for the same change, they're de-duplicated by `fileHash`, so re-anchoring runs once. Slice 3 tests this with a real `git pull` on an open file.
- **Re-anchoring:**
  1. Look for an exact hash match in a window of the same length. If there is exactly one match, move the anchor; status is unchanged.
  2. Otherwise, fuzzy-match the head and tail snippets (line similarity of at least 0.8). A unique candidate gets the anchor moved **and the stale flag set**, so `checked by you` never survives a fuzzy re-anchor clean.
  3. Multiple candidates, or none above the threshold, means orphaned.
- **The hash check runs** on save, after every re-anchor, and on activation.

### Map
- **Dependency:** a Python language server that provides document symbols (the Python extension or Pylance). It's detected when you open the map. With no symbol results, the panel says "Map needs a Python language server (install the Python extension)" and makes no LLM call. If call hierarchy is empty or unavailable, the map groups symbols only and is labeled "no call arrows".
- **Extraction:** top-level classes and functions per `.py` file, respecting `.gitignore` and excluding `.why/` and virtualenvs, plus outgoing calls for each. spike/map-grouping measures extraction time on learningtool against a target under 10 seconds.
- **Grouping output and validation:** `{boxes: [{name, summary, members: [symbolId]}], edges}`. Every `symbolId` must exist in the extracted table; unknown IDs are dropped. A symbol listed in two boxes stays in the first. Symbols not in any box go to a small "Other" box. More than 8 boxes triggers one retry with the limit restated; if it's still over, the extension shows an error instead of a bad map.
- **Click:** a box with one member reveals that symbol. A box with several members expands into a list of its symbols in the panel, and clicking one reveals it.
- **Note-to-box assignment:** take the innermost symbol enclosing the anchor's start, roll it up to its top-level symbol, and use that symbol's box. If no symbol encloses it, use the box holding the most symbols from that file. If the file isn't on the map, use "Other". Counts and amber follow this assignment.
- **Freshness:** `.why/map.json` stores the file hashes it was built from. When the panel opens and any hash differs, a banner reads "Map out of date: N files changed · Regenerate". Symbols from new files appear in "Other" without an LLM call. Deleted members are subtracted from their box, and a box with no members left shows dashed "missing". Regrouping happens only when you click Regenerate, so the cost stays visible. The live part of the map is counts, amber, and the unassigned bucket.

### Privacy and trust
- **What leaves the machine:**
  - explain: the selection with line numbers, the file path, and the enclosing symbol name
  - compare: the guess and the validated claims
  - map: file paths, symbol names and kinds, and call edges (never function bodies)
  - nothing else
- **AI is off per workspace until enabled** with "Margin: Enable AI for this workspace". That choice is stored in `workspaceState`, never in the repo, and the default is off. Atlas stays off by never being enabled. In untrusted workspaces (Workspace Trust restricted mode), notes are displayed read-only, there are no LLM calls, and the webview takes no actions.
- **Webview:** strict CSP (`default-src 'none'`, nonce scripts, styles only from the extension). Note and LLM text are rendered as escaped text; markdown goes through a sanitizer that allows only basic inline formatting. Incoming `postMessage` commands are checked against this complete allowlist, and each one's parameters are validated in the extension host:
  - `reveal {symbolId}`: the ID must exist in the current symbol table
  - `expandBox {boxIndex}`: in range for the current map
  - `openNote {noteId}` / `openDecision {decisionId}`: the ID must match an existing file in `.why/`
  - `relink {noteId}`: starts a host-side pick-a-range flow; the webview never supplies the range
  - `discardNote {noteId}`: destructive, so the extension host shows its own modal confirmation before deleting
  - `regenerate {}`: subject to the per-workspace AI opt-in
  Any other command, or a malformed parameter, is ignored and logged.
- **Comments threads** use `MarkdownString` with `isTrusted = false` and `supportHtml = false`.
- **The self-check log** (reveal-to-save time, guess verdicts) lives in `context.globalStorageUri`, outside the repo and never under `.why/`.

### Decisions
- "Log as decision" saves the note first, then writes `.why/decisions/NNNN-<slug>.md` with the decision, why, date, and `notes: [id, ...]`. Decisions link to note IDs, not raw ranges, so they inherit anchoring and staleness. A decision shows amber in the Decisions tab when any linked note is stale.

### Margin questions
- Only for functions whose definition was added, or whose body changed, in the current save (compared against the last saved version), and that no note covers. At most 3 per file at a time. Dismiss hides the question until that function's body changes again. Untouched existing code never gets one.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R3-1 — consistency (blocking)

**Problem**

> The new reload detection, the watcher/reload de-duplication ('de-duplicated by `fileHash`'), and the unchanged activation/open check all depend on the stored per-note `fileHash` matching the last content the extension accepted, but the design never says when `fileHash` is refreshed. Save persists 'only the changed fields' of shifted anchors, and the immediate-write list names re-anchor results but not `fileHash`. If `fileHash` is not refreshed on every save and after every re-anchor, then undoing back to the saved state (a change event with `isDirty` false) is misread as a reload and discards the user's in-memory shifts, the de-duplication cannot work, and every activation treats the user's own saved edits as outside edits. If it is refreshed per note on every save, every note on the file is rewritten on every save (git churn in a committed `.why/`). This carries forward the unmet R2-6 obligation, now load-bearing for correctness.

**Remedy**

> State explicitly that `fileHash` is refreshed for the file on every save and after every re-anchor or immediate write, and either accept the per-note rewrite or move the per-file hash into a single index (e.g., workspaceState or one `.why/` index file) so note diffs stay limited to real anchor changes.

### R3-2 — consistency (blocking)

**Problem**

> Immediate writes conflict with save-only shifts when the document is dirty. Re-check and Still true compute a new anchor hash (and position) from the current editor buffer and now write it to disk immediately, while the buffer's unsaved edits and the shifts of other notes are only persisted on save. If the user then closes without saving or reverts, the design reloads on-disk note state, but that state now holds a hash and line range describing text that was never saved, so the note immediately mismatches disk and is re-anchored, marked stale, or orphaned on the next activation. The same applies to saving a brand-new note from a selection in a dirty file.

**Remedy**

> Decide the dirty-document rule: either disable Re-check, Still true, and note Save (or prompt to save the file first) while the document is dirty, or hold those writes in memory with the shifts and persist them on save, discarding them on close-without-save like other in-memory state.

### R3-3 — completeness (blocking)

**Problem**

> Reload detection now explicitly covers only clean documents, but outside edits (Claude Code, `git pull`) also hit files that are open with unsaved edits. VS Code does not reload those; the `FileSystemWatcher` (rule 2) still fires, and with 'everything else is written immediately' its re-anchor against disk content would be written to the note file while the buffer holds different text and in-memory shifts that are later persisted on save, overwriting or contradicting the re-anchor. Behavior for the save conflict (overwrite vs. take disk version) is also undefined.

**Remedy**

> Specify that while a document is dirty, watcher-triggered re-anchoring is deferred; on the next save (or on accepting the disk version), re-anchor against the content actually on disk instead of persisting buffered shifts; and test it in slice 3 alongside the clean-file `git pull` test.

### R3-4 — clarity (minor)

**Problem**

> Citations now live in frontmatter as anchor-relative offsets, but the unchanged storage line still says 'The body is the note text with its line citations', implying a second copy with absolute numbers that would go stale. It is also unstated how `claimIndex` maps to claims after the user edits the draft text (claims merged, split, or deleted).

**Remedy**

> State that the body holds claim text only (no line numbers) and define how edits to the draft update or drop `citations` entries.

### R3-5 — feasibility (minor)

**Problem**

> Validating `openNote` / `openDecision` by 'an existing file in `.why/`' can be satisfied by a traversal value (e.g., `../../somefile`) if the ID is joined into a path before the existence check, letting injected webview content open arbitrary workspace files.

**Remedy**

> Validate IDs against a strict pattern (e.g., the short random note ID format or `NNNN-slug`) and look them up in an in-memory index of `.why/` files rather than joining them into a path.

### R3-6 — completeness (minor)

**Problem**

> Persisting R2-5: `discardNote` now gets a host modal confirmation, but discarding a note linked from a decision still leaves a dangling `notes: [id]` link whose display and amber state are undefined.

**Remedy**

> On discarding a linked note, warn in the confirmation and either block the discard or mark the decision link as removed and show that in the Decisions tab.

### R3-7 — consistency (minor)

**Problem**

> Persisting R2-7: the 'Other' box is added after the 8-box limit is enforced, so a map can show 9 boxes, conflicting with premise 6 and the success criterion.

**Remedy**

### R3-8 — feasibility (minor)

**Problem**

> Persisting R2-8: a Python language server that is installed but still starting or indexing returns no symbols, and the panel would wrongly say the language server is missing.

**Remedy**

> Distinguish 'no provider installed' from 'not ready yet' (retry or loading state) before showing the install message.

### R3-9 — completeness (minor)

**Problem**

> Persisting R2-9: for a rename that arrived while VS Code was closed, the 'newly created files' candidate set and its activation cost are undefined.

**Remedy**

### R3-10 — clarity (minor)

**Problem**

**Remedy**

### R3-11 — clarity (minor)

Rename handling, immediate-write policy, citation offsets, Re-check / Still true, webview CSP and allowlist, and map freshness have no owning slice.

**Remedy**

### Unresolved at the cap

1. R3-1 — consistency (blocking): The new reload detection, the watcher/reload de-duplication ('de-duplicated by `fileHash`'), and the unchanged activation/open check all depend on the stored per-note `fileHash` matching the last content the extension accepted, but the design never says when `fileHash` is refreshed. Save persists 'only the changed fields' of shifted anchors, and the immediate-write list names re-anchor results but not `fileHash`. If `fileHash` is not refreshed on every save and after every re-anchor, then undoing back to the saved state (a change event with `isDirty` false) is misread as a reload and discards the user's in-memory shifts, the de-duplication cannot work, and every activation treats the user's own saved edits as outside edits. If it is refreshed per note on every save, every note on the file is rewritten on every save (git churn in a committed `.why/`). This carries forward the unmet R2-6 obligation, now load-bearing for correctness.
2. R3-2 — consistency (blocking): Immediate writes conflict with save-only shifts when the document is dirty. Re-check and Still true compute a new anchor hash (and position) from the current editor buffer and now write it to disk immediately, while the buffer's unsaved edits and the shifts of other notes are only persisted on save. If the user then closes without saving or reverts, the design reloads on-disk note state, but that state now holds a hash and line range describing text that was never saved, so the note immediately mismatches disk and is re-anchored, marked stale, or orphaned on the next activation. The same applies to saving a brand-new note from a selection in a dirty file.
3. R3-3 — completeness (blocking): Reload detection now explicitly covers only clean documents, but outside edits (Claude Code, `git pull`) also hit files that are open with unsaved edits. VS Code does not reload those; the `FileSystemWatcher` (rule 2) still fires, and with 'everything else is written immediately' its re-anchor against disk content would be written to the note file while the buffer holds different text and in-memory shifts that are later persisted on save, overwriting or contradicting the re-anchor. Behavior for the save conflict (overwrite vs. take disk version) is also undefined.
